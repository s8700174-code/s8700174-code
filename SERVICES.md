# Dashboards and practical business tools

I am interested in clearly scoped projects that turn reporting requirements and repetitive workflows into usable software. My public portfolio includes JavaScript dashboard interfaces, Python/FastAPI tools, an Electron desktop application and a WordPress/H5P learning-portal pilot.

## 1. Dashboard prototype

For a team that needs to validate a reporting experience before commissioning a production system.

- Agree on one audience, up to three screens, up to six KPIs and their definitions.
- Build responsive views, coordinated filters, a searchable table and a CSV export using an agreed sample dataset.
- Review two consolidated rounds of feedback against written acceptance criteria.
- Deliver source code, setup instructions and a demonstration walkthrough.

**Relevant example:** [Didban](https://github.com/s8700174-code/didban-dashboard) is a Persian/RTL front-end demonstration with synthetic data. It does not include production authentication, a database or live integrations. Those require a separate technical scope.

## 2. A focused workflow tool

For a team with one repetitive task and a clearly defined input and output.

- Map the existing steps and agree on representative test cases.
- Assess one authorized data source or API, its limits and failure conditions.
- Implement the agreed transformation or workflow, with validation and useful error handling.
- Deliver repeatable checks, operating instructions and source code.

**Relevant example:** [Vazhe](https://github.com/s8700174-code/vazhe-persian-transcriber) demonstrates a local Python/FastAPI transcription workflow. Its published tests cover application behavior with mocked engines; they are not a speech-accuracy benchmark or proof that a particular third-party provider is available.

## 3. Maintenance after delivery

For an application that has passed an agreed handover and acceptance check.

- Maintain a prioritized issue list and an agreed monthly capacity.
- Address reproducible defects and separately estimate feature requests.
- Review relevant dependency updates and document releases.
- Provide a concise monthly work report.

Hours, response windows, hosting responsibilities and exclusions are agreed before work begins. This is not an unlimited-support or 24/7 availability offer.

## How a project starts

Send a short description of the problem, the intended users, sample inputs, expected outputs, preferred deadline and budget. Please use anonymized examples initially.

I assess feasibility before proposing a price or delivery date. A typical milestone plan is:

| Milestone | Acceptance evidence | Share of agreed total |
| --- | --- | --- |
| Scope and prototype | Approved screens, sample data and acceptance checklist | 20% |
| Core implementation | Agreed main workflow works on test cases | 35% |
| Review and verification | Agreed checks pass and review defects are resolved | 30% |
| Handover | Source, operating guide and walkthrough delivered | 15% |

This is an illustrative plan, not a binding quote. Contracting and payment arrangements, third-party costs, access permissions and current capacity must be confirmed for each engagement. Work starts after both parties approve the scope and terms.

## Evidence and boundaries

The repositories identify demonstrations and pilot implementations explicitly. They are not presented as paid client deliveries. No client results, production uptime, certifications or years of experience are implied. Production security, integrations and infrastructure are assessed individually.
